=== Image Editing

The {productname} {release-version} release includes an accompanying release of the **Image Editing** premium plugin.

**Image Editing** includes the following fix.

==== Editing images or applying updates before the image loaded could lose the change
// #TINYMCE-3693

Previously, the **Image Editing** plugin did not wait for an image to finish loading before editing it. Opening the **Edit Image** dialog on an image that was still loading in the editor could cause the dialog to fail. For an image that took several seconds to load, clicking **Edit image** did nothing until the image loaded, with no sign that anything was happening. Inside the dialog, clicking **Apply** on an adjustment, such as a rotation or a brightness change, before its preview finished rendering could discard the adjustment. Users could lose an edit without any warning.

In {productname} {release-version}, the **Image Editing** plugin waits for the image to load before showing the editing tools. When an image is slow to load, the **Edit Image** dialog opens immediately with a **Loading...** message and the **Save** button disabled, then shows the editing tools once the image is ready. Clicking **Cancel** while the image loads closes the dialog. When a user clicks **Apply**, the dialog waits for the latest preview to finish rendering and keeps the adjustment.

For information on the **Image Editing** plugin, see: xref:editimage.adoc[Image Editing].

=== TinyMCE AI

The {productname} {release-version} release includes an accompanying release of the **TinyMCE AI** premium plugin.

**TinyMCE AI** includes the following fixes and addition and improvement.

==== Adding an editor to a group did not add its document to the chat context
// #TINYMCE-15102

Previously, when an editor joined a xref:tinymceai-multi-editor.adoc[multi-editor group] after the group was already in use, the **TinyMCE AI** plugin did not add that editor to the chat context. No context tag appeared for the new editor, and the **Add context source** menu did not list it. Users could not include the content of the new editor in a chat or a group review without reloading the page.

In {productname} {release-version}, when an editor joins a group, the plugin adds a context tag for that editor to the chat immediately, including during a conversation that is already in progress. The **Add context source** menu also lists the new editor, and the next review of the group covers the content of that editor. The chat context stays up to date whenever an editor joins a group.

For information on the **TinyMCE AI** plugin, see: xref:tinymceai-multi-editor.adoc#chat[Chat].

==== Focus now stays on the same AI preview toolbar button when the toolbar moves between editors
// #TINYMCE-14930

Previously, when the **TinyMCE AI** plugin previewed changes in several editors of a xref:tinymceai-multi-editor.adoc[multi-editor group], the shared preview toolbar always focused its first button when it moved to another editor. The toolbar moves when a user steps past the last change in one editor with **Next** or **Previous**, or resolves the last change in an editor with **Apply suggestion** or **Skip suggestion**. Keyboard users then had to move focus back to the button they were using before they could continue, even though the whole group shares a single toolbar.

In {productname} {release-version}, when the preview toolbar moves to another editor, the button the user just pressed receives focus in the new position. Keyboard users can keep pressing the same button to step through, apply, or skip changes across every editor in the group, including when **Next** wraps around from the last change in the group to the first. If that button is disabled in the new position, the toolbar itself receives focus instead. When a user clicks a change in an editor, the toolbar opens with focus on its first button, as before.

For information on the **TinyMCE AI** plugin, see: xref:tinymceai-multi-editor.adoc#previewing-and-applying-changes[Previewing and applying changes].

==== Document context was not restored when resuming a conversation in a single editor with the `+tinymceai_document_name+` option set
// #TINYMCE-14994

Previously, when the xref:tinymceai.adoc#tinymceai_document_name[`+tinymceai_document_name+`] option was set on an editor that was not part of a multi-editor group, reopening a conversation that included the document from the xref:tinymceai-chat.adoc#chat-history[chat history] did not restore the document. The **TinyMCE AI** plugin tried to match the saved document name against the editors of a group. Without a group, the plugin found no match, so no context tag for the editor content appeared above the prompt input. The next prompt did not include the document, and the plugin could not apply the changes that the AI suggested in reply.

In {productname} {release-version}, when a user resumes a conversation in an editor that is not part of a group, the plugin restores the context tag for the editor content, whether or not `+tinymceai_document_name+` is set. The next prompt includes the document, and the plugin can apply the changes that the AI suggests. In a xref:tinymceai-multi-editor.adoc[multi-editor group], when none of the saved document names match an editor in the group, the plugin now attaches the content of every editor in the group, as it does for a new conversation, instead of attaching no document.

For information on the **TinyMCE AI** plugin, see: xref:tinymceai-chat.adoc#current-document-and-selection[Current document and selection].

==== New `+TinyMCEAIDiscardSuggestions+` command to discard the AI suggestions previewed in an editor
// #TINYMCE-15157

Previously, integrations had no public way to discard the AI suggestions previewed in an editor. In decoupled mode, the **TinyMCE AI** plugin does not show its own confirmation dialog before the AI view closes, so an integration that detected pending suggestions could not complete its own prompt to discard them.

In {productname} {release-version}, the new `+TinyMCEAIDiscardSuggestions+` command discards the AI suggestions previewed in the editor it runs on, without applying any of them. The editor keeps the content it had before the preview, and returns to the editor mode it had before the preview. In a xref:tinymceai-multi-editor.adoc[multi-editor group], the command affects only the editor it runs on, so an integration runs the command on each editor in the group to discard every suggestion. For details, see xref:tinymceai.adoc#tinymceai-discard-suggestions[Discarding previewed suggestions].

For information on the **TinyMCE AI** plugin, see: xref:tinymceai.adoc[TinyMCE AI].

=== Changing the width in the Cell Properties dialog now uses the inline column resize logic to ensure the table width does not change
// #TINYMCE-13193

Previously, changing the width in the **Cell Properties** dialog set the new width on the column or cell but did not adjust the other columns. The column widths no longer added up to the table width, so the browser rescaled every column to fit. The edited column often did not display at the entered width, and the other columns changed size unpredictably, so users had to correct them manually.

In {productname} {release-version}, changing the width in the **Cell Properties** dialog resizes the column in the same way as dragging the column border. The next column grows or shrinks to make up the difference, or the previous column when the last column is resized, and the table keeps its width. The dialog keeps the table width regardless of the xref:table-options.adoc#table_column_resizing[`+table_column_resizing+`] option. The adjacent column never shrinks below the minimum cell width. The dialog converts a width entered in pixels or as a percentage to the table's unit. When the table has no width, or the width uses a unit other than pixels or percentages, the dialog sets the width of the selected cells only, as in earlier versions.

=== Inserting an accordion at the end of the content now adds an empty paragraph after it, so the caret can be placed below the accordion
// #TINYMCE-9955

Previously, inserting an accordion at the end of the content left no block below it. Clicking below the accordion did not place the caret, so users had to press Down Arrow from inside the accordion before they could add content after it.

In {productname} {release-version}, the xref:accordion.adoc[Accordion plugin] adds an empty block after an accordion that it inserts at the end of the content. The block uses the element and attributes set by the xref:content-filtering.adoc#forced_root_block[`+forced_root_block+`] and xref:content-filtering.adoc#forced_root_block_attrs[`+forced_root_block_attrs+`] options. By default, the block is a paragraph. Clicking below the accordion places the caret in the new block. Inserting an accordion between existing blocks does not add an empty block.

=== The `+table_appearance_options+` option now also accepts an object with `+cellspacing+`, `+cellpadding+`, `+borderwidth+` and `+caption+` keys, to hide individual fields in the Table Properties dialog
// #TINYMCE-11998

For example, `+table_appearance_options: { cellspacing: false }+` hides only the **Cell spacing** field. The `+true+` and `+false+` values work as before.

[[bug-fixes]]
== Bug fixes

{productname} {release-version} also includes the following bug fix<es>:

=== <TINY-vwxyz 1 changelog entry>
// #TINY-vwxyz1

// CCFR here.

=== Image resize handler was not shown on hybrid devices with both a touchscreen and a mouse or trackpad
// #TINYMCE-14668

Previously, {productname} treated a hybrid device, such as a Windows 2-in-1 laptop, as touch-only whenever the browser reported a touchscreen as the primary pointer, even when a mouse or trackpad was also present. It hid the resize handles on images and tables, and forced table cell selection to use the touch handles instead of the mouse or trackpad.

In {productname} {release-version}, a device that does not run iOS or Android counts as a touch device only when no mouse, trackpad, or other precise pointer is available. On hybrid devices, these options have the same default values as on desktop devices, so the resize handles appear on images and tables. Users of hybrid devices can resize images and select table cells with the mouse or trackpad, without switching to the touchscreen.

=== Formatting text in Firefox 158 and later removed quotes around font names that contain spaces
// #TINYMCE-15130

Previously, in Firefox 158 and later, formatting text that used a font name containing spaces removed the quotes around the font name. For example, applying a text color to a `+span+` element with the style `+font-family: 'arial black'+` changed the style to `+font-family: arial black+`. The cause is a change in Firefox 158: the browser no longer quotes multi-word font names when it rewrites a style attribute, while Chrome and earlier versions of Firefox keep the quotes. Both forms are valid CSS and display the same font, but the HTML returned by xref:apis/tinymce.editor.adoc#getContent[`+editor.getContent()+`] and shown in the source code view depended on the browser. Integrations that compared or stored editor content as text could get different HTML for the same content in different browsers, even though the difference had no visible effect.

In {productname} {release-version}, {productname} adds single quotes around any unquoted font name that contains spaces, so formatted content keeps `+font-family: 'arial black'+` in every browser. {productname} leaves font names that are already quoted, values that use a CSS function such as `+var()+`, and values marked `+!important+` unchanged. Generic font families, such as `+sans-serif+`, are single words and stay unquoted.

=== Resizing the sidebar in a right-to-left editor resized it in the opposite direction to the drag
// #TINYMCE-14904

Previously, when the xref:ui-localization.adoc#language[`+language+`] option was set to a right-to-left language, such as Arabic, dragging the resize handle of a sidebar changed the sidebar width in the opposite direction to the pointer. In a right-to-left editor, the sidebar sits on the left and the resize handle is on the edge next to the editor content. Dragging the handle toward the editor content made the sidebar narrower instead of wider. This affected every sidebar registered with the xref:customsidebar.adoc#resizable[`+resizable+`] property set to `+true+`, including the sidebars of the Comments and {productname} AI plugins, so users of right-to-left languages could not resize these sidebars as expected.

In {productname} {release-version}, the resize handle follows the pointer in right-to-left editors, as it does in left-to-right editors. Dragging the handle toward the editor content widens the sidebar, and dragging it away narrows it. The xref:customsidebar.adoc#sidebar_min_width[`+sidebar_min_width+`] and xref:customsidebar.adoc#sidebar_max_width[`+sidebar_max_width+`] options and the minimum width of the editing area still limit the sidebar width.

=== Clicking to the left or right of an accordion did not place the caret before or after it
// #TINYMCE-9955

Previously, clicking to the left or right of an accordion did not place the caret beside it. Users could not use the mouse to add content directly before or after an accordion, or between two adjacent accordions.

In {productname} {release-version}, clicking to the left or right of an accordion places the caret before or after it, as clicking beside a table does. Typing at that position adds a new paragraph before or after the accordion.

=== It was not possible to place the caret between two adjacent accordions using the arrow keys
// #TINYMCE-9955

Previously, when two accordions were next to each other, pressing Right Arrow at the end of the first accordion moved the caret into the second accordion, and pressing Left Arrow at the start of the second accordion moved the caret into the first. Keyboard users could not place the caret between the accordions to add content there.

In {productname} {release-version}, pressing Left Arrow or Right Arrow to leave an accordion places the caret beside the accordion when another accordion is next to it or when the accordion is at the start or end of the content. From that position, Up Arrow and Down Arrow move the caret into the adjacent accordion or to the adjacent line, and pressing Enter adds a new paragraph.

=== Pressing Delete or Backspace did not remove an empty block before or after an accordion
// #TINYMCE-9955

Previously, pressing Delete in an empty first block directly before an accordion, such as an empty block at the start of the content, did not remove the block. Pressing Backspace in an empty last block directly after an accordion, such as an empty block at the end of the content, also did not remove the block. Users could not remove these empty blocks.

In {productname} {release-version}, pressing Delete in an empty block before an accordion removes the block and moves the caret into the accordion summary. Pressing Backspace in an empty block after an accordion removes the block and moves the caret to the end of the accordion content. When the empty block is inside a container with no other content, such as a list, the editor removes the container as well. The editor never removes a table cell that contains the empty block.

=== Removing bold or italic from a nested list item no longer leaves it styled through inheritance from its parent list item
// #TINYMCE-14935

Previously, when a user made a whole list item bold or italic, any list nested inside it also appeared bold or italic. Removing the formatting from a nested list item had no visible effect, because the nested item still inherited the style from the list item that contained it.

In {productname} {release-version}, removing bold or italic from a nested list item takes effect. The nested item no longer appears bold or italic, and the list item that contains it keeps its formatting.

=== Saving the Table Properties dialog with `+table_appearance_options+` hiding fields no longer removes the table's existing cell spacing, border width or caption
// #TINYMCE-15197

Previously, when the xref:table.adoc#table_appearance_options[`+table_appearance_options+`] option hid fields in the Table Properties dialog, saving the dialog cleared the existing values of the hidden fields on the table. For example, with **Cell spacing**, **Border width**, and **Caption** hidden, changing only the **Width** of a table and clicking **Save** removed the cell spacing of the table and its border width, reset a `+border+` attribute such as `+border="3"+` to `+1+`, and deleted the table caption. The dialog did not show the hidden fields, so users could not see the change or restore the lost values from the dialog.

In {productname} {release-version}, saving the Table Properties dialog leaves the values of hidden fields unchanged on the table. {productname} also no longer applies the xref:table-options.adoc#table_default_styles[`+table_default_styles+`] and xref:table-options.adoc#table_default_attributes[`+table_default_attributes+`] values for a hidden field over the existing value. Saving the dialog changes only the fields that the dialog shows, and the cell spacing, border width, cell padding, and caption of the table stay as they were.

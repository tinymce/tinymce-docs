The {pluginname} plugin allows multiple users to collaborate on a document. The review window shows which user suggested which edits, whether they added, removed, modified, or replaced any content, and allows users to provide feedback on those suggestions or give a final review by accepting or rejecting them.

== How it works

The {pluginname} plugin keeps track of every edit made to the document by the current user and stores this metadata in an internal model of the document. These suggestions can then be reviewed in the Review edits view, where each edit is highlighted in the document, and where users can accept, reject, or provide feedback. The Review edits view opens from either the `suggestededits` toolbar button or the `suggestededits` menu item in the `View` menu.

== The model

The {pluginname} model is a JSON object representing the document along with all unreviewed edits and feedback. The model must be kept in sync with the editor content and loaded into the editor at the same time as the content.

The structure of the model is not documented and should not be relied upon. Models saved by earlier versions of the plugin continue to load and are upgraded automatically.

The model can be retrieved from the plugin using the xref:#get_model[`+getModel+`] API, saved externally alongside the document, and loaded into the editor with the xref:#suggestededits_model[`+suggestededits_model+`] option. This ensures that the document and the model are in sync and every user's contributions are tracked correctly. If the model and content are out of sync when the editor loads, the difference between them will be included in the next edit by the current user. If a model is not provided in the editor configuration or is set to `+undefined+`, the plugin will generate a new model from the initial content.

Alternatively the xref:#suggestededits_content[`+suggestededits_content+`] option allows the model to generate the editor content, in which case the two do not need to be kept in sync.

== Reviewing edits

The Review edits view displays the edits made by multiple authors for review. The available actions in this view depend on the xref:#suggestededits_access[`+suggestededits_access+` option].

While the Review edits view is open, the editor menu bar, toolbar, and status bar remain visible, the editor content is read-only, and the editor can still be resized. Opening a sidebar closes the Review edits view. Opening and closing the Review edits view keeps the current scroll position in the document.

=== Header

The header at the top of the sidebar shows the **Review edits** title and two buttons that end the review:

* Save & Exit: Ends the review, applying resolved suggestions to the document. Unresolved suggestions remain in the document for future review. This button is available only to users with `+full+` access.
* image:icons/close.svg[Exit review icon,24px] Exit review: Ends the review without applying resolved suggestions, and makes no change to the document. Feedback given on suggestions will be retained.

The **Exit review** button displays only an icon. The text **Exit review** appears as a tooltip and as the accessible label of the button.

=== Footer

The footer below the document switches between two views:

* Diff mode: Shows the suggested edits with the color coding described in xref:#document[Document]. While unresolved suggestions remain, Diff mode dims unchanged content so the unresolved suggestions stand out. Diff mode is the default view.
* Preview: Shows how the document reads with the suggested edits applied, taking accepted and rejected suggestions into account. Added and modified content is underlined, and removed content is hidden.

=== Document

The Review edits view displays the current editor document in an iframe, with each suggested edit highlighted where it appears in the document.

In Diff mode, the following color coding is used to indicate the type of change:

* Green: Added content.
* Blue: Modified attributes or formatting, such as bold or italic.
* Red: Removed content, shown with a strikethrough.

In Diff mode, removed images, videos, and embedded frames are also marked with a red X. Line break markers appear only where a line break was added or removed.

Replaced content is represented as both added and removed content, and indicates that some content was removed and replaced with new content in a single edit. When a suggestion is selected, whether in the document or in the sidebar, the corresponding highlighted suggestion in the document will be outlined in blue and scrolled into view. In Diff mode, accepted and rejected suggestions show their result without highlighting, except while the suggestion is selected. Selecting anywhere outside a card or a suggestion clears the selection.

=== Sidebar

Each suggested edit is listed as a card in the sidebar, in the order the edits appear in the document. The card header shows the user who made the suggestion and when the edit was made. Below the header, the card describes the edit and quotes the changed text, for example: Replaced "`the`" with "`them`". Long text is shortened with an ellipsis.

Edits made with the xref:tinymceai.adoc[{productname} AI] plugin are recorded as AI-assisted. An AI badge appears on their cards by default. Set xref:#suggestededits_ai_attribution[`+suggestededits_ai_attribution+`] to `+false+` to hide the badge.

For users with `+full+` access, pointing to a card or selecting it shows the following buttons in the card header:

* Accept: Resolves the suggestion, applying the edit to the document when the review is completed.
* Reject: Resolves the suggestion, turning back the edit to the original state.

After a suggestion is accepted or rejected, the card header shows a **Revert** button with an icon that indicates the decision. Selecting **Revert** removes the decision and returns the suggestion to an unresolved state.

When an unresolved suggestion is selected, users with `+feedback+` or `+full+` access can select **Provide feedback** to open a text area and provide feedback on the suggestion.

Feedback is shown in chronological order beneath the card details when an unresolved card is selected. Feedback allows users to discuss suggestions before resolving them. The feedback author can edit or delete their own feedback, with the appropriate permissions in the xref:#suggestededits_access[`+suggestededits_access+`] option.

==== Bulk actions

Users with `+full+` access can use the **Bulk actions** menu at the top of the sidebar to resolve several suggestions at once:

* Accept all: Accepts every unresolved suggestion. Suggestions that are already accepted or rejected keep their decision. After at least one suggestion is resolved, this item is labeled **Accept remaining**.
* Reject all: Rejects every unresolved suggestion. Suggestions that are already accepted or rejected keep their decision. After at least one suggestion is resolved, this item is labeled **Reject remaining**.
* Revert all: Returns every accepted or rejected suggestion to an unresolved state.

The accept and reject items are unavailable when no unresolved suggestions remain. **Revert all** is unavailable until at least one suggestion is resolved.

=== Keyboard navigation

The Review edits view supports the following keys:

* Tab and Shift+Tab: Move focus between the buttons in the sidebar header, the **Bulk actions** menu, and the cards.
* Up Arrow and Down Arrow: Move between cards and select the focused suggestion.
* Enter: Moves focus into the content of the focused card.
* Escape: Moves focus to the **Exit review** button. When **Exit review** already has focus, Escape ends the review.

=== Finishing a review

When a review is completed with **Save & Exit**, resolved suggestions will be applied to the document and will no longer be tracked in the model as a suggestion. Feedback on resolved suggestions is discarded. Any "accepted" edits will remain in the document, and any "rejected" edits will be reverted to the state before the suggestion was made.

Review actions will apply the following to the document:

When added content is:

* Accepted: The content will remain in the document.
* Rejected: The content will be removed from the document.

When modified content is:

* Accepted: The content will retain the current formats and attributes.
* Rejected: The content will revert to modified formats and attributes to match the content state before the edit was made.

When removed content is:

* Accepted: The content will be removed from the document.
* Rejected: The removed content will be restored to the document.

If a review ends with **Exit review**, no resolved suggestions will be applied to the document. All suggestions, including any feedback provided during that review session, will remain stored in the model.

== Initial setup

To setup the {pluginname} plugin in the editor:

* add `{plugincode}` to the `plugins` option in the editor configuration;
* add `{plugincode}` to the `toolbar` option in the editor configuration;

For example:

[source,js]
----
tinymce.init({
  selector: 'textarea#suggestededits',  // change this value according to your HTML
  plugins: 'suggestededits',
  toolbar: 'suggestededits',
});
----

This configuration adds {pluginname} to the editor toolbar, enabling access to the plugin features. To fully utilize the plugin, additional configuration options must be provided.

Both the xref:#user_id[`+user_id+`] and xref:#fetch_users[`+fetch_users+`] options are required to configure the xref:userlookup.adoc[User Lookup API]. This API is used in the {pluginname} plugin to provide user information for each user who has made a change, allowing other users to see who made which suggestion.

* The current user ID should be set with the xref:#user_id[`+user_id+`] option. The user ID should be a unique string that identifies the user, such as a username or an email address.
* The xref:#fetch_users[`+fetch_users+`] option is required to provide the name and avatar for users who have made suggestions. This option can be configured to fetch data from a backend service. The `+fetch_users+` function is given an array of user IDs and should return a promise, which resolves to an array containing data for the requested user IDs.

== Known Limitations 

[NOTE]
Since the comparison is made against the original version of the document, if there are unresolved changes by multiple authors affecting the same part, the most recent change will be used for comparison. The `hasChanges` API can be used to implement a safeguard that prevents further edits on a document with unresolved changes.

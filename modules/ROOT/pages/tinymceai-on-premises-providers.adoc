= LLM provider configuration
:navtitle: LLM providers
:description: LLM provider configuration for TinyMCE AI on-premises service
:description_short: LLM provider configuration and model catalog.
:keywords: AI, on-premises, LLM, OpenAI, Anthropic, Google, Gemini, Azure, Bedrock, Vertex, Ollama, vLLM, openai-compatible
:pluginname: TinyMCE AI




This page configures *how the AI service reaches LLM providers* and *which models are exposed to clients*. It sits between the xref:tinymceai-on-premises-database.adoc[data layer setup] (which must be complete first) and xref:tinymceai-on-premises-jwt.adoc[JWT authentication] (which gates per-user access to the models configured here). The environment variables documented below are set on the AI service container — in a `docker run` command, a Kubernetes Deployment manifest, or an ECS task definition.

Two environment variables and one JWT claim control provider and model configuration:

* `PROVIDERS`: tells the AI service how to authenticate with each LLM provider API.
* `MODELS`: tells the service which models to expose to clients and which features each model supports.
* `auth.ai.permissions` (JWT claim): gates per-user access to individual models.

This page documents every supported provider `type`, every required field, and every known production issue for both variables.

Start with the xref:tinymceai-on-premises-getting-started.adoc[Getting started guide] if the AI service container is not yet running. The following sections assume a running `ai-service` container.

== Provider and model architecture

The AI service uses two related environment variables:

[cols=",,",options="header",]
|===
|Variable |Type |What it does
|`PROVIDERS` |JSON object |Map of provider IDs to provider configurations. Each entry says how to authenticate with one LLM provider API.
|`MODELS` |JSON array |List of models exposed to clients. Each model points at a `PROVIDERS` entry and declares which features it can serve.
|JSON Web Token (JWT) `auth.ai.permissions` |string array |Per-user authorization list. Includes `ai:models:<provider-key>:<model-id>` entries to gate access to individual models.
|===

The `PROVIDERS` keys are arbitrary identifiers (for example `"openai"`, `"my-bedrock"`, `"team-azure"`). Each value object has a `type` field that picks the implementation:

[cols=",",options="header",]
|===
|`type` |Provider
|`openai` |OpenAI (api.openai.com)
|`anthropic` |Anthropic (api.anthropic.com)
|`google` |Google AI Studio / Gemini direct
|`azure` |Azure OpenAI Service
|`bedrock` |AWS Bedrock
|`vertex` |Google Cloud Vertex AI
|`openai-compatible` |Any OpenAI-compatible HTTP API (Ollama, vLLM, LM Studio, llama.cpp, LocalAI, OpenRouter, Together, Groq, Fireworks, and similar)
|===

The *key* (not the `type`) is what gets referenced from:

* ``MODELS[].provider``; to wire a model to a provider
* JWT `auth.ai.permissions`; for per-provider or per-model access control (see xref:tinymceai-on-premises-jwt.adoc[JWT authentication])

[source,json]
----
{
  "my-openai-key":   { "type": "openai",   "apiKeys": ["sk-proj-..."] },
  "my-bedrock":      { "type": "bedrock",  "region": "us-east-1", "credentials": { "accessKeyId": "...", "secretAccessKey": "..." } },
  "my-ollama":       { "type": "openai-compatible", "baseUrl": "http://host.docker.internal:11434/v1" }
}
----

`GET /v1/models/1` reports the provider `name`, not the provider key, in the `provider` field of each model.

== Defining the model list

=== Default model behavior (`agent-1`)

The OpenAI, Anthropic, and Google providers come with a default list of models. The default list includes `agent-1`, the recommended agent model. Set `MODELS` to replace the default list, and to declare the models of Azure OpenAI, Amazon Bedrock, Google Vertex AI, and openai-compatible providers, which have no default list.

IMPORTANT: Set `MODELS` explicitly for production. Image versions can add models to the default list, so a deployment without `MODELS` can offer different models after an upgrade.

[[startup-validation]]
.Startup validation
[%collapsible]
====
The service validates `PROVIDERS` and `MODELS` when the container starts:

* The service does not start without at least one provider in `PROVIDERS`.
* The service does not start until each conversation, review, and action feature has at least one model to serve it. List `conversations`, `reviews`, and `actions` on at least one model each, or cover each of their sub-features.
* A `MODELS` entry that names a provider key that is not defined in `PROVIDERS` stops startup. See <<multiple-providers-coexistence>>.
* Some features need a model that supports structured output. Models of the same class as the latest major releases from the supported providers give the best results.
====

.Details: `agent-1` behavior and limitations
[%collapsible]
====
* The `/v1/models/1` endpoint reports `agent-1` with `allowed: false` unless the JWT includes the `ai:models:agent` permission.
* Setting `MODELS` explicitly routes each model to the correct provider.
* See xref:tinymceai-on-premises-jwt.adoc[JWT authentication] for permission syntax.
====

For the response format of the model list endpoint, see https://tinymceai.api.tiny.cloud/v1/docs#tag/Models/operation/getAiModels[Fetch all models for a compatibility version] in the API reference. The endpoint only accepts the literal version `1`. Other values return `400 Bad Request`:

[source,bash]
----
# Works
curl http://localhost:8000/v1/models/1

# All 400
curl http://localhost:8000/v1/models/v1
curl http://localhost:8000/v1/models/v2
curl http://localhost:8000/v1/models/latest
----

*Minimum `MODELS` entry* to make a model usable:

[source,json]
----
[
  {
    "id": "gpt-5-mini",
    "provider": "my-openai-key",
    "description": "OpenAI GPT-5 mini",
    "features": ["conversations", "reviews", "actions"]
  }
]
----

The `features` array must include at least one of `conversations`, `reviews`, or `actions` for the model to be selectable for that feature. A model with no overlapping features is invisible to that part of the UI.

A full field reference for `MODELS` is at the end of this page.



== OpenAI

API key from https://platform.openai.com/api-keys[platform.openai.com]. The OpenAI provider comes with a default model list, so it works without an explicit `MODELS` definition, but defining `MODELS` is recommended for production (see <<models-required>>).

.Configuration details
[%collapsible]
====
*JSON shape:*

[source,json]
----
{
  "openai": {
    "type": "openai",
    "apiKeys": ["sk-proj-YOUR_KEY_HERE"]
  }
}
----

*Fields:*

[cols=",,",options="header",]
|===
|Field |Required |Notes
|`type` |Yes |Literal `"openai"`
|`apiKeys` |Yes |Array of one or more API keys. Multiple keys allow zero-downtime rotation.
|`baseUrl` |No |Override only if proxying through a private OpenAI gateway.
|===

*Full `docker run` example:*

[source,bash]
----
docker run --init -d -p 8000:8000 \
  --name ai-service \
  -e LICENSE_KEY="$LICENSE_KEY" \
  -e ENVIRONMENTS_MANAGEMENT_SECRET_KEY="$MANAGEMENT_SECRET" \
  -e DATABASE_DRIVER='mysql' \
  -e DATABASE_HOST='mysql' \
  -e DATABASE_USER='root' \
  -e DATABASE_PASSWORD="$DB_PASSWORD" \
  -e DATABASE_DATABASE='ai_service' \
  -e REDIS_HOST='redis' \
  -e STORAGE_DRIVER='database' \
  -e PROVIDERS='{"openai":{"type":"openai","apiKeys":["sk-proj-YOUR_KEY_HERE"]}}' \
  registry.containers.tiny.cloud/ai-service-tiny:latest
----

*Verify:*

[source,bash]
----
curl -s -H "Authorization: Bearer sk-proj-YOUR_KEY_HERE" \
  https://api.openai.com/v1/models | head -20
----

When that `curl` call succeeds from the host, the same key in `PROVIDERS` works inside the container.

IMPORTANT: *Project-scoped keys* (`sk-proj-...`) only work for models the project has been granted access to. A 404 on `gpt-5.5` usually means the key's project is restricted. *Org-level keys* require the org header, which the service does not send; use a project key instead.
====

curl -s https://api.anthropic.com/v1/models \

== Azure OpenAI

Azure-hosted OpenAI models. Requires an Azure subscription, an Azure OpenAI resource, and at least one deployment. The ``MODELS[].id`` must match the Azure deployment name exactly.

.Configuration details
[%collapsible]
====
*Prerequisites in the Azure portal:*

. Create an Azure OpenAI resource. Note the *resource name*; this is the subdomain prefix in `https://<RESOURCE_NAME>.openai.azure.com`.
. Apply for model access if required by the region.
. In Azure AI Studio, create a *deployment* for each model to expose. Start each deployment name with the ID of the OpenAI model behind it, followed by any suffix (for example `gpt-5-mini-prod`, `gpt-4.1-mini-low-cost`).
. Copy one of the two API keys from *Keys and Endpoint* in the resource overview.

*JSON shape:*

[source,json]
----
{
  "azure": {
    "type": "azure",
    "resourceName": "YOUR_RESOURCE_NAME",
    "apiKeys": ["YOUR_AZURE_KEY_HERE"],
    "apiVersion": "2024-10-21"
  }
}
----

*Fields:*

[cols=",,",options="header",]
|===
|Field |Required |Notes
|`type` |Yes |Literal `"azure"`
|`resourceName` |Yes, unless `baseUrl` is set |The `*.openai.azure.com` prefix only, not the full URL.
|`apiKeys` |Yes, unless `authentication` is set (image version 1.1.0 and later) |Array. Azure issues two keys per resource for zero-downtime key rotation. Set either `apiKeys` or `authentication`, not both.
|`apiVersion` |Yes |The Azure OpenAI API version, sent as the `api-version` query parameter. Always set it explicitly: omitting it produces an SDK error about a missing query string parameter. Refer to https://learn.microsoft.com/azure/ai-services/openai/reference[Microsoft's API version matrix] for current stable values.
|===

IMPORTANT: The ``MODELS[].id`` value must match the Azure *deployment name* exactly, and the deployment name must start with the ID of the OpenAI model it serves, for example `gpt-4.1-editorial` for a `gpt-4.1` deployment. The service reads that prefix to recognize the model family and choose the request options. A `MODELS[].id` that does not match the deployment name produces a `DeploymentNotFound` error.

[[azure-authentication]]
*Authentication and URL options in image version 1.1.0 and later:*

In image version 1.1.0 and later, an Azure OpenAI provider can authenticate with a token instead of API keys. The following example defines a provider that authenticates with Microsoft Entra ID:

[source,json]
----
{
  "azure-entra": {
    "type": "azure",
    "baseUrl": "https://YOUR_RESOURCE_NAME.openai.azure.com",
    "apiVersion": "2024-10-21",
    "authentication": {
      "type": "entra-id",
      "scope": "https://cognitiveservices.azure.com/.default"
    }
  }
}
----

.Additional Azure OpenAI fields
[cols="1,1,3",options="header"]
|===
|Field |Required |Notes
|`baseUrl` |No |Endpoint of the Azure resource, for example `+https://YOUR_RESOURCE_NAME.openai.azure.com+`. Use it instead of `resourceName`.
|`useDeploymentBasedUrls` |No |Defaults to `false`, which sends requests to the Responses API URLs under `+{baseUrl}/v1+`. Set to `true` when the resource exposes only the deployment-based Chat Completions endpoint, `+{baseUrl}/deployments/{model id}/chat/completions+`.
|`authentication.type` |If not using `apiKeys` |`bearer-token` or `entra-id`.
|`authentication.tokenSecret` |For `bearer-token` |Token sent with every request to the Azure endpoint.
|`authentication.scope` |For `entra-id` |Scope requested from Microsoft Entra ID, for example `+https://cognitiveservices.azure.com/.default+`.
|===

With `bearer-token`, the service sends the configured token. With `entra-id`, the service obtains and refreshes tokens through the Azure default credential chain, so the identity comes from the host: environment variables, a managed identity, or a workload identity.

*Two-deployment example:*

[source,bash]
----
-e PROVIDERS='{
  "azure": {
    "type": "azure",
    "resourceName": "tinymce-ai",
    "apiKeys": ["YOUR_AZURE_KEY_HERE"],
    "apiVersion": "2024-10-21"
  }
}'

-e MODELS='[
  {
    "id": "gpt-5-mini-prod",
    "provider": "azure",
    "name": "GPT-5 mini (production)",
    "description": "Azure deployment of GPT-5 mini for production traffic",
    "recommended": true,
    "features": ["conversations", "reviews", "actions"]
  },
  {
    "id": "gpt-4.1-mini-low-cost",
    "provider": "azure",
    "name": "GPT-4.1 mini (low cost)",
    "description": "Azure deployment of GPT-4.1 mini for cheap actions",
    "features": ["reviews", "actions"]
  }
]'
----

*Verify:*

[source,bash]
----
curl -s -H "api-key: YOUR_AZURE_KEY_HERE" \
  "https://YOUR_RESOURCE_NAME.openai.azure.com/openai/deployments?api-version=2024-10-21"
----

Expect a JSON list that includes the deployment IDs from `MODELS`.

IMPORTANT: *Wrong region quota:* each Azure region has independent quotas. Bursty workloads may throttle at modest QPS; split traffic across resources in different regions if needed. *Content filter false positives:* Azure's safety filter is stricter than OpenAI direct. Reviews on certain technical content can return `content_filter` errors. Configure custom content filter policies in Azure AI Studio.

== AWS Bedrock

Amazon's hosted-model marketplace (Anthropic, Meta, Mistral, Cohere, Amazon Titan).

In image versions earlier than 1.2.0, inline the credentials in the `PROVIDERS` JSON: the AWS SDK default credential chain is not used. Image version 1.2.0 and later can also use an assumed role or the credentials of the host. See <<bedrock-newer-credentials>>.

.Configuration details
[%collapsible]
====
WARNING: The AWS SDK reads the `AWS_BEARER_TOKEN_BEDROCK` environment variable as a Bedrock API key, and it takes precedence over `assumedRole` and `credentials`. Leave it unset unless it is the intended identity.

*JSON shape:*

[source,json]
----
{
  "bedrock": {
    "type": "bedrock",
    "region": "us-east-1",
    "credentials": {
      "accessKeyId": "AKIA_YOUR_KEY_HERE",
      "secretAccessKey": "YOUR_SECRET_HERE",
      "sessionToken": "OPTIONAL_FOR_STS"
    }
  }
}
----

The `sessionToken` field is optional but required for STS-issued short-lived credentials. Plan a rotation procedure when using temporary credentials.

Instead of `+credentials+`, a Bedrock provider can set `+apiKeys+` to a Bedrock API key issued in the AWS console.

NOTE: Bedrock console-issued API keys have a separate billing entitlement check that can return `INVALID_PAYMENT_INSTRUMENT` on accounts where the IAM-credential path works fine. Prefer IAM credentials (the `credentials` block, or in image version 1.2.0 and later, an assumed role or the credentials of the host) for production.

[[bedrock-newer-credentials]]
*Assumed role and host credentials in image version 1.2.0 and later:*

The following example defines a provider that assumes a role and a provider that uses the credentials of the host:

[source,json]
----
{
  "bedrock-role": {
    "type": "bedrock",
    "region": "us-east-1",
    "assumedRole": {
      "roleArn": "arn:aws:iam::123456789012:role/tinymce-ai-bedrock",
      "externalId": "YOUR_EXTERNAL_ID",
      "sessionDurationSeconds": 3600
    }
  },
  "bedrock-host": {
    "type": "bedrock",
    "region": "us-east-1"
  }
}
----

.`assumedRole` fields
[cols="1,1,3",options="header"]
|===
|Field |Required |Notes
|`assumedRole.roleArn` |Yes, when `assumedRole` is set |ARN of the IAM role that the service assumes through AWS Security Token Service (STS) before calling Bedrock.
|`assumedRole.externalId` |No |External ID required by the trust policy of the role.
|`assumedRole.sessionDurationSeconds` |No |Lifetime of the temporary credentials, from 900 to 43200 seconds, capped by the maximum session duration of the role. Defaults to the AWS default.
|`assumedRole.roleSessionName` |No |Session name recorded in AWS CloudTrail. Must match `+++^[\w+=,.@-]{2,64}$+++`.
|===

The service authenticates with the first of the following that is configured:

. `assumedRole`: the service calls `sts:AssumeRole` and signs Bedrock requests with the temporary credentials, renewing them before they expire. The `AssumeRole` call uses `credentials` when both are set, and the credentials of the host when `assumedRole` is set on its own. Use this for cross-account access, with the Bedrock permissions attached to the role.
. `credentials`: the service signs requests with the configured access key. Temporary keys also need `sessionToken`, and the service does not renew them.
. `apiKeys`: the service sends the Bedrock API key as a bearer token, with no request signing.
. The credentials of the host: when none of the options above is set, or `apiKeys` resolves to an empty string, the AWS SDK resolves the identity of the machine in its standard order (environment variables, shared AWS configuration files, a web identity token file, the container credentials endpoint, and the instance metadata service). A container on EC2, ECS, or EKS can then reach Bedrock with no secret in `PROVIDERS`.

*Prerequisites checklist:*

. *Enable model access.* Bedrock console -> *Model access* -> Manage model access. Each model must be approved per-region.
. *Subscribe through AWS Marketplace* for non-Amazon models. Anthropic Claude on Bedrock requires a one-time Marketplace subscription.
. *Create an IAM user or role* with the permissions below.
. *Pick a region that has the model.* Not every model is in every region. Check Bedrock console > Model catalog before assuming.

*Required IAM permissions:*

[source,json]
----
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "BedrockInvoke",
      "Effect": "Allow",
      "Action": [
        "bedrock:InvokeModel",
        "bedrock:InvokeModelWithResponseStream",
        "bedrock:Converse",
        "bedrock:ConverseStream"
      ],
      "Resource": "*"
    }
  ]
}
----

The service uses both `InvokeModel` and `Converse` paths depending on the model family, so include both.

*Claude cross-region inference profiles:*

Recent Claude models on Bedrock use *cross-region inference profiles* rather than per-region model IDs. The ``MODELS[].id`` must be the inference profile ID, prefixed with the regional group. For example, the US profile ID for Claude Sonnet 5 is `us.anthropic.claude-sonnet-5`.

The region groups and profile IDs differ for each model. Check the model card in the Amazon Bedrock documentation for the profiles of the model in use.

Using the bare model ID (`anthropic.claude-sonnet-5`) returns `ValidationException`.

*Minimal example:*

[source,bash]
----
-e PROVIDERS='{
  "bedrock": {
    "type": "bedrock",
    "region": "us-east-1",
    "credentials": {
      "accessKeyId": "AKIA_YOUR_KEY_HERE",
      "secretAccessKey": "YOUR_SECRET_HERE"
    }
  }
}'

-e MODELS='[
  {
    "id": "us.anthropic.claude-sonnet-5",
    "provider": "bedrock",
    "name": "Claude Sonnet 5 (Bedrock)",
    "description": "Anthropic Claude Sonnet 5 through AWS Bedrock cross-region inference",
    "recommended": true,
    "capabilities": { "reasoning": true },
    "features": ["conversations", "reviews", "actions"]
  }
]'
----

*Verify before running the AI service:*

[source,bash]
----
aws bedrock list-foundation-models --region us-east-1 \
  --query 'modelSummaries[?contains(modelId,`claude`)].[modelId,modelLifecycle.status]' \
  --output table
----

[source,bash]
----
aws bedrock-runtime converse \
  --region us-east-1 \
  --model-id us.anthropic.claude-sonnet-5 \
  --messages '[{"role":"user","content":[{"text":"Say hello in five words."}]}]'
----

If either fails, the AI service fails with the same root cause; fix IAM and model access before continuing.

IMPORTANT: *`AccessDeniedException`* almost always means missing model access in the Bedrock console. *`ThrottlingException`* on the first call indicates low default quotas; request an increase through Service Quotas. *`ValidationException`* means a mismatch between regional model IDs and cross-region inference profiles. *`INVALID_PAYMENT_INSTRUMENT`* indicates a missing AWS Marketplace subscription.

[[google-vertex-ai]]
== Google Vertex AI

Google's enterprise model surface. Project-scoped, IAM-driven, GCP-billed.

In image versions earlier than 1.2.0, inline a service account key or an account-bound API key in the `PROVIDERS` JSON: Application Default Credentials are not used. Image version 1.2.0 and later can also use impersonation or the credentials of the host. See <<vertex-newer-credentials>>.

.Configuration details
[%collapsible]
====
IMPORTANT: An API key authenticates Gemini models only. Requests to Claude models on Vertex AI always need a Google OAuth token. Give a provider that serves Claude models `credentials`. In image version 1.2.0 and later, `impersonation` or a host with Application Default Credentials also work.

*JSON shape (service account):*

[source,json]
----
{
  "vertex": {
    "type": "vertex",
    "project": "YOUR_GCP_PROJECT_ID",
    "location": "us-central1",
    "credentials": {
      "clientEmail": "ai-service@YOUR_GCP_PROJECT_ID.iam.gserviceaccount.com",
      "privateKey": "-----BEGIN PRIVATE KEY-----\nMIIE...\n-----END PRIVATE KEY-----\n"
    }
  }
}
----

*JSON shape (account-bound API key):*

[source,json]
----
{
  "vertex": {
    "type": "vertex",
    "project": "YOUR_GCP_PROJECT_ID",
    "location": "us-central1",
    "apiKeys": ["YOUR_VERTEX_API_KEY"]
  }
}
----

*Fields:*

[cols=",,",options="header",]
|===
|Field |Required |Notes
|`type` |Yes |Literal `"vertex"`
|`project` |Yes |GCP project ID, not the project number. Can also come from the `GOOGLE_VERTEX_PROJECT` environment variable.
|`location` |Yes |Region, for example `us-central1`, `europe-west4`. Must support the model family. Can also come from the `GOOGLE_VERTEX_LOCATION` environment variable.
|`credentials.clientEmail` |If using SA |The `client_email` field from the SA JSON key.
|`credentials.privateKey` |If using SA |The `private_key` field from the SA JSON key. See the newline escaping note below.
|`apiKeys` |If using account-bound key |Array of one or more Vertex-bound API keys.
|===

[[vertex-newer-credentials]]
*Impersonation and host credentials in image version 1.2.0 and later:*

The following example defines a provider that impersonates a service account and a provider that uses the credentials of the host:

[source,json]
----
{
  "vertex-impersonation": {
    "type": "vertex",
    "project": "YOUR_GCP_PROJECT_ID",
    "location": "us-central1",
    "impersonation": {
      "targetPrincipal": "ai-service@YOUR_GCP_PROJECT_ID.iam.gserviceaccount.com",
      "lifetimeSeconds": 3600
    }
  },
  "vertex-host": {
    "type": "vertex",
    "project": "YOUR_GCP_PROJECT_ID",
    "location": "us-central1"
  }
}
----

.`impersonation` fields
[cols="1,1,3",options="header"]
|===
|Field |Required |Notes
|`impersonation.targetPrincipal` |Yes, when `impersonation` is set |Email of the service account to impersonate.
|`impersonation.lifetimeSeconds` |No |Lifetime of the access tokens issued for that service account. Defaults to `3600`, maximum `43200`.
|===

The service authenticates with the first of the following that is configured:

. `impersonation`: the service requests a short-lived access token for `targetPrincipal` from the IAM Credentials API, scoped to `+https://www.googleapis.com/auth/cloud-platform+`, and renews it as it expires. The token request uses `credentials` when both are set, and the credentials of the host when `impersonation` is set on its own. Grant the source identity `roles/iam.serviceAccountTokenCreator` on the target service account.
. `credentials`: the service signs a JWT with the service account key and exchanges it for an access token.
. `apiKeys`: the service calls Vertex AI in express mode with the API key (Gemini models only).
. The credentials of the host: when none of the options above is set, the Google auth library resolves Application Default Credentials in its standard order (the file that `GOOGLE_APPLICATION_CREDENTIALS` points to, the file written by `gcloud auth application-default login`, and the service account attached to the host). A container on Google Cloud can then reach Vertex AI with no secret in `PROVIDERS`.

*`private_key` newline escaping:*

When copying the `private_key` from a GCP service account JSON key into a `.env` file and then expanding with `set -a && source .env`, the shell collapses the `\n` sequences and the key becomes invalid (Vertex returns `invalid_grant`). A reliable approach is to build the entire `PROVIDERS` value using a JSON serializer:

[source,bash]
----
python3 - <<'EOF' > providers.json
import json
sa = json.load(open("/path/to/service-account.json"))
providers = {
    "vertex": {
        "type": "vertex",
        "project": sa["project_id"],
        "location": "us-central1",
        "credentials": {
            "clientEmail": sa["client_email"],
            "privateKey": sa["private_key"]
        }
    }
}
print(json.dumps(providers))
EOF

export PROVIDERS="$(cat providers.json)"
----

*Account-bound API keys still require a service account:*

The Vertex "account-bound API key" is bound to a Google Cloud project AND a service account inside that project. A service account must exist and have `roles/aiplatform.user` granted; the API key only avoids distributing the private key.

*GCP org policies that block setup:*

[cols=",",options="header",]
|===
|Org policy |Blocks
|`iam.disableServiceAccountCreation` |Creating the service account. Symptom: `403 Permission iam.serviceAccounts.create denied`.
|`iam.disableServiceAccountKeyCreation` |Downloading a JSON key. Symptom: *Create key* greyed out, or `FAILED_PRECONDITION`.
|`iam.allow.disabled` |Account-bound API key creation. Symptom: `API_KEY_INVALID`.
|===

When a GCP org enforces any of these, the security or cloud team must grant a project-level exception or pre-provision the credentials.

*Minimal example:*

[source,bash]
----
-e PROVIDERS='{
  "vertex": {
    "type": "vertex",
    "project": "tinymce-ai",
    "location": "us-central1",
    "credentials": {
      "clientEmail": "ai-service@tinymce-ai.iam.gserviceaccount.com",
      "privateKey": "-----BEGIN PRIVATE KEY-----\nMIIEv...\n-----END PRIVATE KEY-----\n"
    }
  }
}'

-e MODELS='[
  {
    "id": "gemini-3.8-flash",
    "provider": "vertex",
    "name": "Gemini 3.8 Flash (Vertex)",
    "description": "Google Gemini 3.8 Flash through Vertex AI",

*Verify:*

== OpenAI-compatible (Ollama, vLLM, LM Studio, and similar)

Use this provider type for any runtime or aggregator that is not listed as a native provider above but exposes an OpenAI-compatible `/v1/chat/completions` endpoint — including Ollama, vLLM, LM Studio, OpenRouter, Together, Groq, and Fireworks.

The `baseUrl` *must* include the `/v1` suffix.

=== Configuration

[source,json]
----
{
  "local-llm": {
    "type": "openai-compatible",
    "baseUrl": "http://host.docker.internal:11434/v1",
    "apiKeys": ["optional-bearer-token"],
    "headers": { "X-Custom-Header": "value" }
  }
}
----

[cols="1,1,3",options="header"]
|===
|Field |Required |Notes
|`type` |Yes |Literal `"openai-compatible"`
|`baseUrl` |Yes |*Must include the `/v1` suffix.* Without it, every request fails with a misleading "Not Found" Server-Sent Events (SSE) error.
|`apiKeys` |No |Sent as `Authorization: Bearer <key>`. Most local runtimes ignore it.
|`headers` |No |Additional headers such as auth tokens or tenant IDs.
|===

NOTE: File uploads through this adapter are limited to `image/*` MIME types. PDFs and Office documents are not forwarded. To work with non-image files, route through an OpenAI, Anthropic, or Bedrock provider instead.

=== Ollama networking

Ollama listens on `127.0.0.1:11434` by default, which is unreachable from inside a Docker container. Bind to all interfaces:

[source,bash]
----
OLLAMA_HOST=0.0.0.0:11434 ollama serve
----

On Linux with systemd, create an override file instead:

[source,ini]
----
# /etc/systemd/system/ollama.service.d/override.conf
[Service]
Environment="OLLAMA_HOST=0.0.0.0:11434"
----

Then reload and restart: `sudo systemctl daemon-reload && sudo systemctl restart ollama`.

On Linux, add the host gateway so `host.docker.internal` resolves:

[source,yaml]
----
services:
  ai-service:
    image: registry.containers.tiny.cloud/ai-service-tiny:latest
    extra_hosts:
      - "host.docker.internal:host-gateway"
----

If Ollama returns "does not support tools", the model was built from a raw GGUF without a chat template. Use `ollama pull` for a Library model that includes a proper Modelfile, or author a custom one.

.Custom Modelfile example
[%collapsible]
====
[source]
----
FROM /path/to/your-model.gguf

TEMPLATE """{{ if .System }}<|im_start|>system
{{ .System }}<|im_end|>
{{ end }}{{ range .Messages }}<|im_start|>{{ .Role }}
{{ .Content }}<|im_end|>
{{ end }}<|im_start|>assistant
"""

PARAMETER stop "<|im_end|>"
PARAMETER stop "<|im_start|>"
----

The exact template depends on the base model. Check the model card for the recommended chat template. Verify tool support with `ollama show <model>` before connecting to the AI service.
====

The reasoning toggle (`capabilities.reasoning: true`) is cosmetic for Ollama-backed models; the openai-compatible adapter does not translate it to the native Ollama API.

== Multiple providers coexistence

`PROVIDERS` is a single JSON object that may contain any number of entries. Each entry is independent; the service maintains a separate client pool per provider. There is no limit beyond JSON-in-env-var size constraints (many shells allow 64 KB{plus} or more in a single variable).

A `MODELS` array routes individual models to specific providers using the `provider` field, which must match a `PROVIDERS` key.

=== Example: three providers, mixed routing

}'

    "provider": "openai",

[[model-resolution-order]]
=== Model resolution order

Feature strings form a dot-separated hierarchy: in `reviews.correctness`, the parent feature is `reviews`. The service routes a request as follows:

* A request goes to a model that declares the most specific matching feature. A request for `reviews.correctness` goes to a model that declares `reviews.correctness`, even when a model that declares `reviews` comes earlier in `MODELS`.
* A feature with no exact match falls back to its parent. When models declare only `reviews` and `reviews.correctness`, a `reviews.clarity` request goes to the model that declares `reviews`.
* When several models declare the same feature, the order of `MODELS` ranks them. When the service picks the model for a feature, the first model serves the request, and the next one serves it when the first model is unavailable (see <<model-availability>>).

[[agent-models]]
== Custom agent models

`MODELS` can define custom agent models. A custom agent model is a virtual model that calls no provider itself. It lists standard models in `fallbackOrder`, and each request goes to the first model on that list that is available. When none of them is available, the request fails.

[source,bash]
----
-e MODELS='[
  {
    "id": "claude-sonnet-5",
    "provider": "anthropic",
    "description": "Anthropic Claude Sonnet 5",
    "capabilities": { "reasoning": true }
  },
  {
    "id": "gpt-5-mini",
    "provider": "openai",
    "description": "OpenAI GPT-5 mini",
    "capabilities": { "reasoning": true }
  },
  {
    "type": "agent",
    "id": "writing-assistant",
    "name": "Writing assistant",
    "description": "Uses the first available model from two providers",
    "recommended": true,
    "capabilities": { "reasoning": true },
    "features": ["conversations", "reviews", "actions"],
    "fallbackOrder": ["claude-sonnet-5", "gpt-5-mini"]
  }
]'
----

An agent model accepts the same fields as a standard model (`id`, `name`, `description`, `recommended`, `capabilities`, `contextLimits`, and `features`), with these differences:

* `type` must be `agent`.
* `fallbackOrder` is required. It is a non-empty, ordered array of `id` values of standard models in the same `MODELS` array.
* The service ignores `provider`. Each request uses the provider of the standard model that serves it.

When an agent model sets `capabilities.webSearch` or `capabilities.reasoning` to `true`, every model in its `fallbackOrder` must set the same capability. Otherwise the service fails to start with a validation error.

Clients see an agent model as an ordinary model in the model list. The list never includes its `fallbackOrder` or the providers of the models behind it.

Agent models can replace or reorder the models behind a stable model ID, for example to roll out a newer model or retire an old one, without changing editor configuration or JWT permissions. They also keep the choice of models and providers private to the deployment, and continue to answer during a provider outage when they list models from more than one provider.

[[model-availability]]
=== Model availability

The service tracks the health of every model and takes an unhealthy model out of rotation for 60 seconds. All replicas share this state through Redis, so a model that is out of rotation is out of rotation on every replica.

* A model leaves rotation after three failed requests, or three responses that took more than 10 seconds to produce the first token, within 5 minutes. The service counts failures and slow responses separately, and one healthy response resets both counts.
* After 60 seconds, the service sends one probe request to the model. If it succeeds, the model returns to rotation. If it fails, the model stays out for another 60 seconds.
* The service picks the model before it sends a request, and does not switch models during a request.

A request to a standard model that is out of rotation fails, because there is nothing to fall back to. An agent model uses the first model in its `fallbackOrder` that is in rotation, and fails only when none is. To keep requests working during a provider outage, offer an agent model that lists models from at least two providers.



[[rotating-api-keys]]
== Rotating API keys without downtime

The `apiKeys` field on every provider type that has one is an *array*. The service uses the first key, and if the provider rejects that key as invalid, the next one. To rotate a key without downtime, add the new key after the current one, restart, then remove the old key:

. Append the new key to the array:
+
[source,json]
----
"apiKeys": ["sk-proj-OLD_KEY", "sk-proj-NEW_KEY"]
----
. Restart the AI service container so it picks up the new `PROVIDERS` value.
. Verify the new key directly against the provider, with the *Verify* command in the provider section above. The service keeps using the first key until the provider rejects it.
. Revoke the old key in the provider console.
. Remove the old key from `apiKeys`:
+
[source,json]
----
"apiKeys": ["sk-proj-NEW_KEY"]
----
. Restart the AI service container again.

The same procedure works for `anthropic`, `google`, `azure`, and `openai-compatible` provider types. For Bedrock and Vertex, swap the `credentials` object atomically; there is no array of credential objects, so plan a short maintenance window or run two AI service replicas behind a load balancer for a no-downtime swap. In image version 1.2.0 and later, a Bedrock or Vertex AI provider that uses an assumed role, impersonation, or the credentials of the host has no static keys in `PROVIDERS` to rotate, unless the assumed role or impersonation also uses `credentials`.
